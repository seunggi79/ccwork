# 태그 기능 PRD

`spec-fixed.md`(확정된 제품/UX 결정)를 기반으로 한 PRD. 기술 결정(ADR)은 3가지 아키텍처 안
(안 A 최소 확장 / 안 B 분리형 / 안 C 즉시 저장형)을 비교한 뒤 **안 B(분리형)**로 확정했다.

## 개요

노트에 태그를 추가/삭제하고, 노트 상세(편집) 화면에서 태그 목록을 확인할 수 있게 한다. 태그는
문자열로 저장하며 노트당 중복 태그는 허용하지 않는다. 자세한 데이터 구조, UI 패턴, 엣지케이스
결정은 [`spec-fixed.md`](./spec-fixed.md) 참고.

## 사용자 스토리

1. 노트를 작성/편집하는 사용자로서, 노트에 태그를 자유롭게 추가하고 싶다. 그래야 노트를
   주제/카테고리별로 분류할 수 있다.
2. 노트를 편집하는 사용자로서, 잘못 추가했거나 더 이상 필요 없는 태그를 개별적으로 삭제하고
   싶다. 그래야 태그 목록을 정확하게 유지할 수 있다.
3. 노트를 확인하는 사용자로서, 노트 상세(편집) 화면에서 이 노트에 붙은 태그 목록을 한눈에
   보고 싶다.
4. 노트를 편집하는 사용자로서, "저장"을 누르기 전까지는 태그 변경 사항이 실제로 반영되지
   않았으면 한다. 그래야 "취소"로 태그 추가/삭제를 포함한 모든 변경을 안전하게 되돌릴 수 있다.
5. 노트를 편집하는 사용자로서, 같은 태그를 대소문자나 앞뒤 공백만 다르게 여러 번 입력해도
   중복으로 추가되지 않았으면 한다. 그래야 의미상 같은 태그가 여러 벌 생기지 않는다.
6. 새 노트를 작성하는 사용자로서, 노트를 처음 저장하는 시점부터 태그를 함께 지정하고 싶다.
   그래야 태그 없는 노트를 만든 뒤 다시 편집해서 태그를 추가하는 두 단계를 거치지 않아도 된다.

## 기술 결정 (ADR)

3가지 아키텍처 안을 데이터 구조/API/상태 관리/즉시 저장 여부/컴포넌트 구조/기존 패턴과의
일관성/테스트 용이성 7개 기준으로 비교했다.

- **안 A (최소 확장)**: 데이터 구조·저장 시점은 `spec-fixed.md` 그대로, 태그 로직 전부를
  `NoteEditor.tsx`에 인라인으로 구현. 기존 패턴과 가장 잘 맞지만 태그 로직만 따로 단위 테스트할
  방법이 없다(`NoteEditor` 전체를 렌더링해야 함).
- **안 B (분리형, 채택)**: 데이터 구조·저장 시점은 안 A와 동일하되, 태그 입력 UI를
  `TagInput` 컴포넌트로, 중복 판단/정규화 로직을 순수 함수로 분리해 테스트 용이성을 확보.
- **안 C (즉시 저장형)**: 칩 추가/삭제를 클릭 즉시 서버에 반영. `spec-fixed.md`가 "취소 시 태그
  변경도 함께 폐기"를 요구사항으로 명시했는데, 즉시 저장은 이미 반영된 태그를 취소로 되돌릴 수
  없어 그 요구사항과 정면으로 충돌한다. 채택하지 않고, 왜 배치 저장(안 A/B)을 택했는지 보여주는
  대조군으로만 남긴다.

**결론: 안 B 채택.** 아래 4개 ADR에 반영.

### ADR-001: 태그 데이터 구조

- **Context**: 태그를 노트 객체에 직접 내장할지, 별도 `tags` 컬렉션을 두고 관계로 관리할지
  결정이 필요했다. json-server는 관계형 조인(`_expand`/`_embed`)을 온전히 지원하지 않고,
  현재 태그를 독립 엔티티로 관리해야 할 요구사항(이름 변경, 색상 지정 등)이 없다.
- **Decision**: `Note.tags: string[]`로 노트 객체에 직접 내장한다. 별도 `tags` 컬렉션을
  두지 않는다.
- **Alternatives**: 별도 `tags` 컬렉션 + 노트가 `tagIds: string[]`로 참조 — 관계형 조인이
  번거롭고, 지금 없는 "태그 자체를 독립적으로 관리"하는 요구사항을 미리 가정하는 과설계라
  기각.
- **Consequences**: 태그 이름 일괄 변경, 태그별 통계 같은 기능이 필요해지면 이 데이터 구조를
  다시 바꿔야 한다. 대신 지금은 API/Context 변경이 최소화되고 구현이 단순하다.

### ADR-002: 태그 입력 컴포넌트 아키텍처

- **Context**: `spec-fixed.md`는 조기 추상화 방지를 이유로 `NoteEditor` 인라인 구현을 잠정
  결정했지만, 안 A/B/C 비교에서 인라인 방식은 태그 로직만 독립적으로 단위 테스트할 방법이 없다는
  약점이 확인됐다.
- **Decision**: 태그 입력 UI(입력창 + 칩 목록)를 `src/components/TagInput.tsx`
  프레젠테이셔널 컴포넌트로 분리한다. 상태(`tags`/`tagInput`)는 계속 `NoteEditor`가 소유하고,
  `TagInput`은 `tags`/`onAdd`/`onRemove` props만 받는다 (`NoteList`→`NoteItem`의
  컨테이너/프레젠테이셔널 분리 패턴과 동일한 모양).
- **Alternatives**: 안 A(전부 `NoteEditor` 인라인) — `spec-fixed.md`의 원래 결정 및
  CLAUDE.md의 "조기 추상화 금지" 원칙에는 가장 부합하지만, 테스트 용이성에서 명확히 열위라
  기각.
- **Consequences**: 이 프로젝트에서 `NoteEditor`가 처음으로 자식 입력 컴포넌트를 갖게 된다
  (title/content는 여전히 인라인). "왜 태그만 분리했는가"에 대한 근거(테스트 용이성)를 코드
  리뷰 시 남겨둘 필요가 있다.

### ADR-003: 태그 상태 관리 방식

- **Context**: 상태와 로직을 어디까지 분리할지 — 로컬 `useState` 그대로 둘지, 커스텀 훅으로
  캡슐화할지, 로직만 순수 함수로 뺄지 결정이 필요했다. 이 프로젝트엔 아직 커스텀 훅이나
  `utils/` 디렉토리 전례가 없다.
- **Decision**: 상태(`tags`, `tagInput`)는 `NoteEditor`가 `useState`로 계속 소유한다. 중복
  판단/trim/정규화 로직만 `src/utils/tags.ts`의 순수 함수(예: `addTag(tags, input): string[]`)
  로 뽑아서, 상태 관리 자체는 기존 패턴을 유지하되 로직만 테스트 가능한 단위로 분리한다.
- **Alternatives**: 커스텀 훅 `useTagInput()`으로 상태+로직을 통째로 캡슐화 — 프로젝트에 훅
  분리 전례가 전혀 없는 상태에서 과한 추상화로 판단해 기각. 안 A(로직도 인라인) — 순수 함수
  단위 테스트가 불가능해 기각.
- **Consequences**: `NotesContext.createNote(title, content)`는 `(title, content, tags)`로
  확장된다(안 A/B 공통 사항). `src/utils/`가 이 프로젝트 최초로 생기며, 이후 다른 순수 로직도
  이곳에 모으는 관례의 출발점이 된다.

### ADR-004: 태그 칩 스타일 구현 방식

- **Context**: `docs/design-system/components.md`는 태그 칩을 pill이 아닌 hairline 사각형 +
  `×` 글리프로 규정한다 (`spec-fixed.md`의 옛 `rounded-full` pill 언급은 디자인 시스템 도입
  이전 내용이라 더 이상 유효하지 않음). ADR-002에서 `TagInput` 컴포넌트를 분리하기로 했으니,
  이 스타일을 그 컴포넌트 안에 구현할지 더 잘게 쪼갤지 결정이 필요했다.
- **Decision**: 칩 스타일은 `TagInput.tsx` 내부에 직접 구현한다. 별도의 공용 `Chip`
  컴포넌트로는 추출하지 않는다. `docs/design-system/components.md` 기준(hairline 사각형,
  `--color-muted` 배경, 1px 보더, `×` 글리프)을 그대로 따른다.
- **Alternatives**: 재사용 가능한 공용 `src/components/Chip.tsx`로 분리 — 현재 태그 칩 외에
  칩/배지 UI가 필요한 곳이 이 앱에 없어(예: `NoteItem`은 배지를 쓰지 않음), 재사용 사례 없이
  미리 추상화하는 것은 과설계로 판단해 기각.
- **Consequences**: 나중에 태그 칩과 비슷한 UI(예: 상태 라벨, 다른 배지)가 다른 곳에도
  필요해지면, 그때 `TagInput`에서 `Chip`을 다시 뽑아내는 리팩터링이 필요할 수 있다.

## Out of Scope

이번 태그 기능 구현에서 **하지 않는** 것들. 각 항목이 왜 범위 밖인지, 어떤 대안/향후 가능성이
있는지 최대한 구체적으로 남긴다.

- **태그 자동완성 / 기존 태그 재사용 UI**: 노트 전체를 순회해 태그 집합을 만들고 입력 중
  드롭다운으로 보여주는 기능. 초기 버전은 자유 텍스트 입력만 지원하며, 태그 개수가 늘어나
  재사용 필요성이 커지면 별도 기능으로 다룬다.
- **태그로 노트 필터링/검색**: 사이드바 노트 목록을 태그 기준으로 좁히거나, 특정 태그가 달린
  노트만 모아보는 기능. 이번 스펙은 "태그 부착/조회"까지만 다루고, "태그를 활용한 탐색"은
  범위 밖이다.
- **태그 개수/길이 제한**: 노트당 최대 태그 개수, 태그 문자열 최대 길이 제한을 두지 않는다.
  향후 실제 사용 패턴에서 UI가 깨지는 사례가 나오면 그때 구체적인 숫자로 추가한다.
- **사이드바 노트 목록(`NoteItem`)에 태그 배지 표시**: 태그는 노트 상세(편집) 화면에서만
  보여준다. 목록 항목에 태그를 표시하려면 레이아웃 변경과 "몇 개까지 보여줄지/넘치면 어떻게
  자를지"라는 새로운 디자인 결정이 필요한데, 이는 별도 요구사항으로 다룬다.
- **태그 이름 변경**: 이미 여러 노트에 붙은 태그의 표기를 일괄로 바꾸는 기능. 태그가 독립
  엔티티가 아니라 각 노트에 개별 문자열로 저장되므로, 이름 변경을 지원하려면 ADR-001에서
  다루는 데이터 구조 자체를 바꿔야 한다.
- **태그별 색상/아이콘 지정**: YEEZY 디자인 시스템은 완전 모노크롬이 원칙이라(색상은 destructive
  예외만 허용), 태그마다 다른 색을 주는 것은 디자인 시스템과도 상충한다.
- **태그 통계/카운트 뷰**: "가장 많이 쓴 태그", "태그별 노트 개수" 같은 집계 화면.
- **태그 일괄 작업(bulk)**: 여러 노트를 선택해 한 번에 태그를 추가/삭제하는 기능. 현재 앱에
  다중 선택 UI 자체가 없다.
- **서버(API) 계약 변경**: `src/api/notes.ts`의 함수 시그니처나 `res.ok`/`throw new Error`
  패턴을 바꾸지 않는다. 태그는 기존 `Note` 필드들과 동일하게 요청 본문에 실려 가는 값 중
  하나로만 취급한다.
- **기존 노트 데이터 마이그레이션 스크립트**: `db.json`의 태그 없는 기존 노트들을 일괄
  변환하는 스크립트를 만들지 않는다. `tags: selectedNote.tags ?? []` 형태의 런타임 하위 호환
  처리로 충분하다고 보고, 저장(수정) 시점에 자연스럽게 `tags` 필드가 채워지도록 둔다.
- **접근성(a11y) 전용 작업**: 태그 칩의 키보드 내비게이션, 스크린리더 라벨링 등을 별도로
  설계하지 않는다. 프로젝트 전반에 걸친 a11y 작업이 아직 없는 상태이므로, 이 기능만 별도로
  선행하지 않는다.
- **다국어(i18n)**: 태그 관련 문구도 프로젝트 전체와 동일하게 한국어 고정이며, 다국어 지원
  체계 자체가 이 프로젝트에 없다.

## 용어 정의

| 용어        | 정의                                                                                                                |
| ----------- | ------------------------------------------------------------------------------------------------------------------- |
| 태그(Tag)   | 노트를 분류하기 위해 붙이는 문자열 하나. `Note.tags: string[]`의 원소 하나를 가리킨다.                              |
| 칩(Chip)    | 노트 편집 화면에서 태그 하나를 시각적으로 표현하는 UI 단위(텍스트 + 개별 삭제 버튼).                                |
| 태그 입력창 | 새 태그를 타이핑해서 추가하는 텍스트 입력 필드. Enter 입력 시 현재 값을 태그로 추가하고 입력창을 비운다.            |
| 중복 태그   | `trim()` 후 대소문자를 무시했을 때 이미 목록에 있는 태그와 같은 문자열. 추가 시도 시 조용히 무시된다.               |
| 생성 모드   | `NoteEditor`가 `isCreating=true`일 때의 상태. 아직 서버에 저장되지 않은 새 노트를 작성 중인 화면.                   |
| 편집 모드   | `NoteEditor`가 특정 `selectedNoteId`를 가리킬 때의 상태. 기존 노트의 필드(제목/내용/태그)를 수정하는 화면.          |
| 저장        | `NoteEditor`의 "저장" 버튼 클릭 시 `createNote`/`updateNote`를 호출해 로컬에 반영된 태그 변경을 서버로 보내는 동작. |
| 취소        | `NoteEditor`의 "취소" 버튼 클릭 시 로컬에만 있던 태그(및 제목/내용) 변경 사항을 폐기하고 편집을 종료하는 동작.      |
