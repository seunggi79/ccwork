# /create-pr

현재 브랜치의 커밋을 PR로 올린다. 핵심은 **PR을 만들기 전에 E2E로 실제 동작을 확인한다**는
것이다 — 리뷰어가 "돌아가긴 하나?"를 직접 확인하지 않아도 되게 만드는 게 이 스킬의 목적이다.

```
현재 브랜치 (커밋 완료 상태)
    ↓ 0단계 — 전제 조건 확인 (브랜치·작업 트리·gh 인증·기존 PR)
    ↓ 1단계 — base 브랜치 결정 + 변경사항 요약 → PR 초안 작성
    [GATE] 초안 승인 (사용자가 제목/본문 수정 가능)
    ↓ 2단계 — npm run test:e2e 실행          ← 승인 후에만 실행한다
    ├─ 실패 → PR 생성 중단 + 진단 안내 (아래 "E2E 실패 시" 절)
    └─ 통과 ↓
    ↓ 3단계 — git push
    ↓ 4단계 — gh pr create
    ↓ 5단계 — PR URL 보고
```

**왜 E2E를 초안 승인 뒤에 돌리는가**: E2E는 3개 브라우저에서 30초 내외가 걸린다. 제목이나
base 브랜치가 잘못돼 어차피 다시 해야 할 상황에서 먼저 테스트를 돌리면 그 시간이 버려진다.
사람이 "이 내용으로 올리자"고 확정한 뒤에 검증하는 편이 낭비가 없다.

## 언제 쓰나

- "PR 만들어줘 / 올려줘 / 보내줘", "이거 머지하자" 같은 요청이 올 때
- TDD 이슈 사이클 7단계(커밋 → push → PR)에 도달했을 때
- `/create-pr`로 직접 호출되었을 때

이 스킬이 하지 않는 것: PR 머지, `gh issue close`(머지 이후의 일), 새 기능 구현, E2E 스펙
수정.

## 0단계 — 전제 조건 확인

아래를 순서대로 확인하고, 막히면 그 지점에서 멈춘다.

1. **현재 브랜치가 `main`이 아닐 것.** `main`이면 PR을 만들 수 없으므로, 브랜치를 새로 파고
   커밋을 옮길지 사용자에게 묻는다.
2. **작업 트리 상태.** `git status --porcelain`으로 확인하되, 두 종류를 구분한다.
   - **추적 중인 파일의 미커밋 변경(`M`)**: 멈춘다. PR에는 커밋된 것만 들어가므로 그대로
     두면 사용자가 의도한 내용과 PR 내용이 어긋난다. 무엇이 남아 있는지 보여주고 커밋할지
     스태시할지 확인받는다. **이 스킬이 임의로 커밋하거나 스태시하지 않는다.**
   - **추적되지 않은 파일(`??`)**: 무조건 멈추지 않는다. 이 저장소에서는 `.claude/skills/`의
     새 스킬이나 스크래치 파일이 흔히 남아 있고, 그게 PR 범위와 무관한 경우가 많다. 목록을
     보여주고 "이번 PR에 포함할 것이 섞여 있는지"만 확인한 뒤 진행 여부를 묻는다.
   - 참고로 `db.json`은 json-server가 실행 중 다시 쓰는 런타임 파일이라 앱이나 E2E를 한 번
     돌리기만 해도 `M`으로 잡힌다. 내용상 의미 있는 변경이 아니면 그 사실을 알려준다.
3. **올릴 커밋이 있을 것.** `git log --oneline {base}..HEAD`가 비어 있으면 멈춘다.
   **주의**: "아직 push하지 않은 커밋 수"와 "base 대비 커밋 수"는 다르며, PR에 들어가는 것은
   **후자**다. 스펙 브랜치처럼 이미 여러 하위 PR이 머지된 브랜치에서는 base(`main`) 대비
   커밋이 훨씬 많을 수 있다 — 이때 PR 제목·본문은 방금 쌓은 커밋 몇 개가 아니라 **base 대비
   전체 변경**을 설명해야 한다. 두 숫자가 다르면 사용자에게 그 사실을 함께 알린다.
4. **`gh` 인증.** `gh auth status`로 확인한다. 인증이 안 돼 있으면 `gh auth login`은 대화형
   입력이 필요하므로 사용자가 직접 실행해야 한다고 안내한다.
5. **열려 있는 PR이 있는지.** `gh pr view --json url,state`로 확인하고, **`state`가 `OPEN`일
   때만** 기존 PR로 취급해 새로 만들지 말고 push로 갱신할지 묻는다. `MERGED`/`CLOSED`인 PR은
   갱신할 수 없으므로 없는 것으로 보고 그대로 진행한다 — 같은 브랜치가 이전에 머지된 이력이
   있으면 여기에 과거 PR이 잡히는데, 이걸 열린 PR로 오해해 멈추면 안 된다.

## 1단계 — base 브랜치 결정 + PR 초안

### base 브랜치

`CLAUDE.md`의 규칙상 **기본값은 `main`이 아니다.**

- 이슈 작업 브랜치(예: `feature/tag-create`, `feature/tag-delete`)는 그 기능의 **스펙
  브랜치**(예: `feature/tag-spec`)를 base로 한다. 선행 이슈가 그 브랜치에 머지돼 있어야
  변경이 올바르게 쌓인다.
- 스펙 브랜치 자체(예: `feature/tag-spec`)를 올릴 때만 base가 `main`이 된다.

판단 근거를 추측으로 때우지 말고 실제로 확인한다: `git log --oneline {후보}..HEAD`로 어느
브랜치 기준으로 커밋이 쌓였는지 보고, `gh pr list --state all`로 같은 기능의 이전 PR들이
어디를 base로 썼는지 확인한다(이 저장소에는 이미 전례가 있다). 그래도 애매하면 **추측하지
말고 사용자에게 묻는다** — base를 잘못 잡으면 남의 커밋까지 딸려 들어간 PR이 만들어진다.

### 제목

이 저장소의 기존 PR 관례를 따른다.

- **이슈 작업 브랜치**: `TAG-2(#6): 편집 중인 노트에서 태그 삭제` —
  `{이슈 라벨}(#{번호}): {한 줄 요약}`
- **스펙 브랜치 → `main`**: 이슈 하나가 아니라 기능 전체가 올라가므로 이슈 라벨을 쓸 수 없다.
  commitlint 타입 접두사 + 기능 단위 요약으로 쓴다 (예:
  `feat: 태그 기능(TAG-1~2) 구현 및 E2E 환경 구축`). 여러 타입의 커밋이 섞여 있으면 그중
  **사용자 가치 기준으로 가장 큰 것**을 접두사로 삼는다 — 기능 추가가 하나라도 있으면 `feat`,
  문서만이면 `docs`, 설정/빌드만이면 `build`/`chore`.

### 본문

`git log {base}..HEAD`와 `git diff {base}...HEAD --stat`을 실제로 읽고 쓴다. 커밋 메시지를
그대로 나열하지 말고, **리뷰어가 알아야 할 것**으로 재구성한다 — 무엇이 바뀌었고, 왜 그렇게
했고, 무엇을 확인했는지.

스펙 브랜치처럼 범위가 넓으면 diffstat이 수십 개 파일로 나와 한눈에 파악되지 않는다. 이때는
`git log --oneline --merges {base}..HEAD`로 이미 머지된 하위 PR 단위를 먼저 파악해 덩어리로
나눈 뒤, 각 덩어리를 한 줄씩 요약하는 편이 파일 목록을 훑는 것보다 정확하다.

```markdown
## Summary

- (변경의 핵심을 1~4개 불릿으로. 파일 목록이 아니라 "무엇을 할 수 있게 됐는지")

## Test plan

- [ ] `npm run test:e2e` — 승인 후 실행 예정

🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

**Test plan은 게이트 시점과 PR 생성 시점의 내용이 다르다.** E2E는 승인 뒤(2단계)에 돌리므로,
게이트에서 보여주는 초안에는 아직 확인되지 않은 항목을 체크된 것처럼 적으면 안 된다 —
그건 실행하지도 않은 결과를 사용자에게 보고하는 셈이다.

- **게이트 초안**: `- [ ] npm run test:e2e — 승인 후 실행 예정`
- **PR 생성 시(2단계 통과 후)**: 실제 숫자로 바꿔 채운다 —
  `- [x] npm run test:e2e — 18/18 통과 (chromium/firefox/webkit)`

이미 이 세션에서 돌려 결과를 아는 항목(`npm test`, `npx tsc --noEmit` 등)은 그 숫자를 그대로
체크해 적어도 된다. 반대로 **실행하지 않은 것은 아예 쓰지 않는다** — 빈 체크박스를 남겨두면
리뷰어가 "이건 왜 안 했지?"를 매번 물어야 한다.

Summary에 적는 내용은 **실제 diff에 있는 것만** 쓴다. 커밋 메시지나 기능 이름에서 동작을
추측해 "~도 한다"고 덧붙이지 않는다 — 예를 들어 태그 정규화 로직에 개수 제한이나 소문자
변환이 있다고 단정하기 전에 `src/utils/tags.ts`를 실제로 열어 확인한다. 사실과 다른 PR 설명은
리뷰어를 잘못된 방향으로 이끈다.

UI 변경이 포함됐다면 스크린샷 대신 어떤 화면이 어떻게 달라지는지 문장으로 적는다.

## [GATE] 초안 승인

제목·base 브랜치·본문 전체를 사용자에게 보여주고 승인을 받는다. 사용자가 문구를 고치겠다고
하면 반영한 뒤 다시 보여준다. **승인 전에는 테스트도, push도, PR 생성도 하지 않는다.**

## 2단계 — E2E 실행

승인을 받은 뒤 `npm run test:e2e`를 실행한다(chromium/firefox/webkit 3개 브라우저, 30초 내외).

- **전부 통과** → 3단계로 진행하고, 통과 숫자를 본문 Test plan에 반영한다.
- **하나라도 실패** → **PR을 만들지 않고 즉시 중단**한다. 아래 절의 안내를 출력한다.

## E2E 실패 시 — PR 생성 중단 및 진단 안내

실패했다면 push도 PR 생성도 하지 않는다. 사용자에게 실패한 테스트 이름과 함께 아래 순서를
안내한다.

**① 실패 지점 확인**

```bash
npx playwright show-report
```

HTML 리포트에 실패한 테스트의 에러 메시지와 실패 시점의 페이지 스냅샷(`error-context.md`)이
들어 있다. 대부분은 이것만으로 원인이 보인다.

단, **로컬에서는 Trace Viewer에 볼 트레이스가 없다.** `playwright.config.ts`가
`retries: 0`(로컬) + `trace: 'on-first-retry'`라서 재시도가 일어나지 않으면 트레이스가 아예
기록되지 않기 때문이다. 타임라인·DOM 스냅샷·네트워크까지 봐야 한다면 해당 파일만 트레이스를
켜서 다시 돌린다:

```bash
npx playwright test e2e/{파일}.spec.ts --trace on
npx playwright show-trace test-results/{...}/trace.zip
```

**② 어느 레이어에서 깨졌는지 판별**

| 레이어 | 신호                                            | 확인할 곳                                          |
| ------ | ----------------------------------------------- | -------------------------------------------------- |
| API    | 저장/조회가 반영 안 됨, 새로고침 후 값이 사라짐 | `src/api/notes.ts`, json-server 응답, `db.json`    |
| 렌더링 | 요소를 못 찾음, 화면에 안 나타남                | 해당 컴포넌트의 JSX, 로케이터가 가리키는 마크업    |
| 로직   | 값은 있는데 계산/상태가 틀림                    | `src/utils/`, `NotesContext`, 컴포넌트의 상태 전이 |

**먼저 제품 버그인지 인프라 문제인지 가른다.** 간헐적으로만 실패하거나 "요소는
visible/enabled/stable인데 클릭이 타임아웃"되는 형태라면 제품 버그가 아닐 가능성이 높다 —
`CLAUDE.md`의 "테스트 설정 메모"에 적힌 설정(특히 `vite.config.ts`의 `server.watch.ignored`로
`db.json`을 Vite 감시에서 제외하는 것)이 유지되고 있는지부터 확인한다. 이 설정이 빠지면
json-server의 `db.json` 쓰기가 브라우저 전체 새로고침을 일으켜 화면 상태가 날아간다.

**③ 해당 단위 테스트에 케이스 추가 (Red)**

E2E가 잡아낸 결함을 재현하는 케이스를 **단위/컴포넌트 테스트(`*.test.ts(x)`)에 먼저 추가**해
실패시킨다. E2E는 느리고 원인을 좁혀주지 않으므로, 같은 결함을 빠르고 정확한 계층에서
고정해두는 것이다. 이렇게 해야 다음에 같은 버그가 재발할 때 30초짜리 E2E가 아니라 1초짜리
단위 테스트가 먼저 잡아준다.

**④ 프로덕션 코드 수정 (Green) → 다시 `/create-pr`**

추가한 단위 테스트가 통과하도록 `src/`를 고친다. 그다음 `/create-pr`을 다시 실행하면 초안
승인부터 E2E까지 같은 흐름을 다시 탄다.

**⚠️ E2E 스펙을 고쳐서 통과시키지 않는다.** 단언을 완화하거나 대기를 넣거나 실패하는 테스트를
지우는 것은 근본 원인 회피이며, 그렇게 통과한 PR은 "테스트가 있다"는 착각만 남기고 실제
버그를 그대로 배포한다.

예외는 하나뿐이다 — 제품이 **의도적으로** 바뀌어서 E2E 스펙이 낡은 경우(예: 버튼 문구를
일부러 바꿔 로케이터가 안 맞음). 이때도 스스로 판단해 고치지 말고, 무엇이 왜 낡았는지
사용자에게 설명하고 명시적으로 승인을 받은 뒤에만 스펙을 수정한다.

## 3단계 — push

먼저 upstream 유무를 확인하고, 그 결과에 맞는 명령을 쓴다.

```bash
git rev-parse --abbrev-ref --symbolic-full-name @{u}   # 먼저 확인
git push                                               # upstream이 이미 있을 때
git push -u origin HEAD                                # upstream이 없을 때 (첫 push)
```

push가 거부되면(원격이 앞서 있음) 임의로 `--force`하지 않고 상황을 사용자에게 보고한다.

## 4단계 — PR 생성

본문에 백틱·따옴표·줄바꿈이 많으므로 셸 인용 문제를 피하려면 본문을 파일로 넘긴다.

```bash
gh pr create --base {base} --title "{제목}" --body-file {경로}
```

본문 임시 파일은 저장소 안이 아니라 스크래치패드 디렉토리에 만든다(저장소를 더럽히지 않기
위해).

## 5단계 — 보고

생성된 PR URL과 함께 요약한다: base 브랜치, 커밋 수, E2E 결과.

머지와 `gh issue close {N}`은 **하지 않는다.** `CLAUDE.md`의 사이클상 머지는 사람이 리뷰 후
수행하고, 이슈 종료는 머지 다음이다. 다만 다음 단계로 무엇이 남았는지는 알려준다.

## 제약

- 사용자 승인 없이 push하거나 PR을 만들지 않는다.
- E2E가 실패한 상태로 PR을 만들지 않는다.
- E2E 스펙(`e2e/*.spec.ts`)을 통과시킬 목적으로 수정하지 않는다.
- 미커밋 변경을 임의로 커밋하거나 스태시하지 않는다 — 무엇을 할지 사용자에게 확인받는다.
- `git push --force`를 임의로 쓰지 않는다.
- PR 머지, 이슈 종료를 하지 않는다.
