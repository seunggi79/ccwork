  TDD처럼 아직 없는 기능을 위해 실패하는 테스트를 먼저 쓰는 것이 아니다.

# /e2e-write

`docs/features/{기능명}/prd.md`의 사용자 스토리를 입력으로 받아, 실제로 구현된 스토리만 골라
Playwright E2E 테스트로 옮기는 스킬이다.

```
docs/features/{기능명}/prd.md (사용자 스토리)
    ↓ 0단계 — PRD·Playwright 설정 존재 확인
    ↓ 1단계 — 스토리별 구현 여부 확인 (소스 코드 기준, GitHub 이슈 상태는 교차 확인용)
    ↓ 2단계 — 단위/컴포넌트 테스트가 이미 덮는 범위 파악 (중복 방지 기준선)
    ↓ 3단계 — 구현된 스토리마다 E2E 시나리오 초안 작성
    [GATE] 시나리오 승인
    ↓ 4단계 — 테스트 인프라(fixture) 준비
    ↓ 5단계 — e2e/{기능명}.spec.ts 작성
    ↓ 6단계 — 즉시 실행 → 통과 확인 (실패 시 원인 진단, 임의로 단언 완화 금지)
    ↓ 7단계 — prd.md에 "E2E 커버리지" 섹션 기록 + 결과 요약 보고
```

TDD 사이클(`/test-scenarios` → `/tdd-red` → `/tdd-green` → `ac-verifier` →
`/tdd-refactor` → `/tdd-security-gate`)이 "아직 없는 기능을 만들기 위한 실패하는 테스트"를
다루는 것과 달리, 이 스킬은 **이미 구현되어 커밋·머지까지 끝난 기능**을 실제 브라우저에서
한 번 더 확인하는 회귀 테스트를 만든다. 그래서 작성한 테스트는 처음 실행부터 통과해야
정상이다 — 실패한다면 테스트가 잘못됐거나(셀렉터, 타이밍), 드물게는 배포된 코드에 실제
버그가 있다는 신호다.

## 언제 쓰나

- 사용자가 기능명을 주며 E2E/브라우저 테스트를 만들어달라고 할 때
- `/e2e-write {기능명}`으로 직접 호출되었을 때
- 한 기능의 TDD 이슈들이 다 머지된 뒤, "실제로 붙여서 돌아가는지" 마지막으로 한 번 더
  확인하고 싶을 때

이 스킬이 하지 않는 것: `src/`의 구현 코드를 고치는 것, `*.test.ts(x)`(Vitest) 테스트를
쓰거나 수정하는 것, 아직 구현되지 않은 스토리를 위한 테스트를 미리 써두는 것(그건 실패하는
E2E를 남겨 다음 기능 작업을 방해한다), 커밋/PR 생성.

## 입력

`$ARGUMENTS`: `docs/features/` 아래의 기능 디렉토리 이름 (예: `tag` → `docs/features/tag/`).

## 0단계 — 전제 조건 확인

1. `docs/features/{기능명}/prd.md`가 없으면 멈추고, 먼저 `/feature-planner`로 PRD부터
   만들라고 안내한다. 이 스킬은 PRD 없이는 "사용자 스토리"라는 입력 자체가 없다.
2. `playwright.config.ts`와 `e2e/` 디렉토리가 없으면 멈추고, Playwright 설치·설정부터 하라고
   안내한다(`npm install -D @playwright/test` + `npx playwright install`). 이 스킬은 기존
   Playwright 설정을 전제로 시나리오/스펙 파일만 다룬다 — 전역 설정(브라우저 프로젝트 목록,
   `webServer`, `baseURL`)을 새로 만들거나 바꾸지 않는다.

## 1단계 — 스토리별 구현 여부 확인

PRD의 "## 사용자 스토리" 목록을 하나씩 순회하며, **지금 코드가 실제로 그 스토리를 만족하는지**
직접 관련 소스를 읽어 판단한다. 이 판단이 이 스킬에서 가장 중요한 단계다 — 잘못 판단하면
아직 없는 기능을 테스트하는 죽은 E2E를 남기거나(계속 실패), 이미 되는 기능을 빠뜨린다.

- **소스 코드가 1차 근거다.** 관련 컴포넌트(`src/components/`), Context(`NotesContext.tsx`),
  API 레이어(`src/api/notes.ts`)를 읽고, 스토리 문장이 묘사하는 사용자 행동이 지금 코드
  경로상 실제로 가능한지 확인한다.
- **GitHub 이슈 상태는 교차 확인용 참고 자료일 뿐, 최종 근거가 아니다.**
  `docs/features/{기능명}/issues.md`에서 스토리를 구현하는 이슈(들)를 찾고
  `gh issue view {N} --json state`로 open/closed를 확인해볼 수는 있지만, **이슈가 열려
  있다고 무조건 "미구현"으로 단정하지 않는다.** 실제로 이 프로젝트에는 후속 이슈의 부수
  효과로 어떤 스토리가 먼저 구현되어 있는데도(예: 편집 화면을 열 때 기존 태그를 보여주는
  로직이 앞선 이슈 작업에 이미 포함되어 있었던 경우) 그 스토리를 다루는 이슈 자체는 아직
  열려 있는 경우가 있었다. 이슈 상태와 코드가 어긋나면 **코드를 믿고**, 그 불일치를 7단계
  보고에 남긴다.
- 한 스토리가 여러 이슈에 걸쳐 있으면(예: "취소 시 되돌리기"가 여러 이슈의 완료 조건에 각각
  흡수된 경우), 그 이슈들이 실제로 구현하는 코드 경로를 전부 확인해야 그 스토리를 "구현됨"으로
  볼 수 있다.
- 판단 결과를 표로 정리한다: `스토리 번호 | 요약 | 구현 여부 | 근거(파일:줄, 관련 이슈)`.
  구현되지 않은 스토리는 이유와 함께 목록에 남기고 이후 단계에서 제외한다.

## 2단계 — 단위/컴포넌트 테스트가 이미 덮는 범위 파악

E2E는 브라우저·서버·DB까지 실제로 띄우는 만큼 가장 느리고 깨지기 쉬운 테스트 계층이다.
Vitest(jsdom, API 모킹)가 이미 확인해준 것을 E2E에서 또 확인하는 것은 시간 낭비이자 유지보수
부담만 늘리는 중복이다. 구현된 스토리마다:

- `docs/features/{기능명}/issue-{N}.md`의 "## 테스트 시나리오" 절(있다면)을 읽어 어떤
  정상/경계/예외 케이스가 이미 Vitest로 커버됐는지 확인한다.
- 문서가 없거나 못 미덥다면 실제 `*.test.ts(x)` 파일을 열어 무엇을 단언하는지 직접 본다.
- 이 정보로 "E2E가 새로 검증해야 할 것"과 "이미 충분히 검증된 것"을 가른다. 판단 기준은 다음
  절 참고.

## 3단계 — E2E 시나리오 초안

구현이 확인된 스토리마다 아래 두 종류로만 시나리오를 뽑는다. 그 외의 것(대소문자/공백 처리,
빈 입력 무시, 개수 제한 없음 같은 입력값 경계 케이스)은 이미 순수 함수/컴포넌트 단위에서
훨씬 저렴하게 검증되므로 **의도적으로 만들지 않는다**.

1. **스토리당 핵심 해피 패스 1개**: "사용자가 이 스토리에 묘사된 행동을 실제 화면에서 하면,
   눈에 보이는 결과가 그대로 나오는가"를 브라우저 조작 → 화면 확인으로 검증한다. 함수 호출
   여부나 내부 상태가 아니라, 사용자가 보는 것(텍스트, 칩, 목록)만 단언한다.
2. **단위 테스트가 구조적으로 확인할 수 없는 것**: jsdom + API 모킹으로는 만들 수 없는
   전체 스택 결합 검증. 이 프로젝트에서 대표적으로:
   - **새로고침/재조회 후에도 값이 남아있는가** (실제 HTTP 왕복 + `db.json` 영속화 확인 —
     Vitest는 `api/notes.ts`를 모킹하므로 이걸 검증할 수 없다)
   - **여러 화면/컴포넌트를 넘나드는 흐름** (예: 노트 A를 편집 → 다른 노트 B 선택 → 다시 A로
     돌아왔을 때도 일관된 상태인지 — 컴포넌트 하나만 렌더링하는 RTL 테스트로는 안 됨)

시나리오 문장 형식은 프로젝트의 기존 테스트 네이밍과 맞춰 영어로 쓴다:
`should [기대 동작] when [사용자 행동]` (예: `should keep the newly added tag chip visible
after reloading the page`).

## [GATE] 시나리오 검토

뽑은 시나리오 목록(스토리 → 시나리오 문장 → 왜 이걸 골랐는지/무엇을 의도적으로 뺐는지)을
사용자에게 보여주고 승인을 받는다. 이미 구현된 기능에 대한 회귀 테스트라 TDD만큼 무겁게
게이트를 걸 필요는 없지만, "몇 개나 쓸지/무엇을 뺄지"는 사람이 한 번 보고 조정할 여지를
남긴다.

## 4단계 — 테스트 인프라 준비

E2E는 실제로 떠 있는 json-server와 `db.json`을 상대로 돈다. 이 프로젝트는 별도의 테스트
전용 DB를 두지 않는 대신(포트가 `src/api/notes.ts`에 하드코딩돼 있어 분리하려면 그 파일까지
바꿔야 하고, 이 스킬은 `src/`를 건드리지 않는다), **테스트가 만든 데이터는 테스트가 끝나면
반드시 스스로 지운다**. 이 정리를 매 테스트 파일마다 새로 작성하지 않도록 공용 fixture를
쓴다.

- `e2e/support/fixtures.ts`가 있는지 확인한다. 없으면 이 스킬의 `assets/fixtures.ts`를 그
  경로로 복사한다. 이미 있다면 덮어쓰지 않는다 — 대신 `notesApi.create`/`notesApi.track`/
  `notesApi.findByTitle`을 제공하는지 확인하고, 시그니처가 다르면 사용자에게 알리고 어떻게
  맞출지 확인한다.
- 이 fixture가 하는 일: API로 노트를 만들면(`notesApi.create`) 생성된 id를 기억해뒀다가,
  테스트가 끝나면(성공/실패 무관) 자동으로 삭제한다. UI로 노트를 만드는 시나리오(예: 새 노트
  생성 자체가 검증 대상인 경우)는 생성 후 `notesApi.findByTitle`로 찾아 `notesApi.track(id)`로
  등록해 똑같이 자동 정리되게 한다.
- **왜 "API로 준비하고 UI로 검증"하는가**: 어떤 스토리를 확인하려면 보통 노트 하나가 이미
  존재해야 한다(예: 태그 삭제를 테스트하려면 태그가 붙은 노트가 먼저 있어야 함). 그 전제
  조건 자체가 검증 대상이 아니라면, 매번 "제목 입력 → 저장 버튼 클릭"을 반복하는 대신 API로
  1초 안에 만드는 게 낫다 — 테스트가 빨라지고, 그 전제 단계에서 나는 실패와 실제 검증 대상의
  실패를 헷갈리지 않게 된다. 반대로 "생성 자체"가 스토리의 핵심이면(예: 새 노트를 태그와
  함께 최초 저장하는 시나리오) 그 부분만큼은 반드시 실제 UI 폼을 통해 수행해야 그 스토리를
  검증한 것이 된다.

## 5단계 — 스펙 파일 작성

`e2e/{기능명}.spec.ts`에 승인된 시나리오를 옮긴다.

```typescript
import { test, expect } from './support/fixtures';

test.describe('{PRD 제목 또는 기능명, 한글}', () => {
  test('should ... when ...', async ({ page, notesApi }) => {
    const note = await notesApi.create({ tags: ['react'] });

    await page.goto('/');
    await page.getByRole('heading', { name: note.title }).click();
    // ... 조작 ...

    await expect(page.getByText('react')).toBeVisible();
  });
});
```

**로케이터 원칙**: 이 코드베이스에는 `data-testid`가 없다. 새로 추가하지 말고(그건 `src/`를
건드리는 일이라 이 스킬의 범위 밖이다), 이미 있는 접근성 속성으로 충분히 안정적인 로케이터를
만든다 — `getByRole`, `getByPlaceholder`, `getByText`. `page.locator('.class-name')`처럼
Tailwind 클래스에 의존하는 로케이터는 스타일 리팩터링 한 번에 깨지므로 쓰지 않는다.

이 프로젝트 구조에서 자주 필요한 패턴:

- **노트 선택**: 사이드바 항목은 별도 role이 없는 `<div onClick>`이지만, 제목이
  `<h3>`(heading role)로 렌더링되고 클릭 이벤트가 버블링되므로
  `page.getByRole('heading', { name: title, exact: true }).click()`으로 충분하다.
- **태그 칩 삭제 버튼**: 칩마다 `×` 텍스트의 버튼이 반복되므로 태그 이름으로 특정 칩을 먼저
  좁혀야 한다. `TagInput.tsx`는 `{tag}<button>×</button>`을 구분자 없이 그대로 렌더링하므로
  칩의 `textContent`는 `"react×"`처럼 태그명과 `×`가 붙은 문자열이다 — **정확히 일치하는
  정규식(`^${tag}$`)은 이 이유로 절대 매칭되지 않는다.** `hasText`의 기본 부분 문자열
  매칭을 그대로 쓴다(이 앱에서 `<span>`은 태그 칩에만 쓰이므로 다른 텍스트와 혼동될 위험은
  없다):
  ```typescript
  const chip = page.locator('span').filter({ hasText: tag });
  await chip.getByRole('button', { name: '×' }).click();
  ```
- **주요 버튼**: `getByRole('button', { name: '저장' })`, `getByRole('button', { name: '취소' })`,
  `getByRole('button', { name: '+ 새 노트' })`.
- **입력 필드**: `getByPlaceholder('제목')`, `getByPlaceholder('태그 추가')`.
- **새로고침 후 상태 확인**: `await page.reload()` 뒤 다시 같은 노트를 열어 확인한다 — 이게
  바로 2/3단계에서 말한 "단위 테스트가 구조적으로 못 하는 것"의 실제 구현이다.

**단언 원칙**: `waitForTimeout` 같은 고정 대기를 쓰지 않는다. Playwright의 `expect(locator)`는
기본적으로 요소가 나타나거나 조건이 성립할 때까지 자동으로 재시도하므로, 네트워크 왕복이나
리렌더링을 기다릴 때도 그냥 `await expect(...).toBeVisible()` 형태로 쓰면 된다. 함수 호출
여부(`updateNote`가 이런 인자로 불렸는지)는 이미 컴포넌트 테스트가 모킹으로 확인했으므로,
E2E에서는 절대 검증하지 않고 **화면에 보이는 결과**만 본다.

## 6단계 — 실행 및 검증

`npx playwright test e2e/{기능명}.spec.ts`로 방금 쓴 스펙만 실행한다. chromium·firefox·webkit
3개 브라우저가 모두 정상 동작하므로(WebKit 구동용 시스템 라이브러리는 설치 완료), 브라우저를
좁히지 말고 설정된 프로젝트 전체로 실행한다. 브라우저가 아예 기동되지 않는 실패(`Missing
libraries` 배너와 함께 나는 실패)를 만나면 그건 테스트 결함이 아니라 환경 문제이므로,
단언을 고치려 들지 말고 `sudo npx playwright install-deps {브라우저}`가 필요하다는 점을
사용자에게 알린다(비밀번호 입력이 필요해 사용자가 직접 실행해야 한다).

**전부 통과해야 정상이다.** 이미 구현·머지된 기능을 검증하는 것이므로 Red 상태가 나오면 안
된다. 실패했다면:

1. 먼저 로케이터/타이밍 등 테스트 코드 자체의 문제인지 의심하고 고친다.
2. 그래도 재현되면 실제 앱 동작이 스토리/AC와 다르다는 뜻일 수 있다 — 이럴 땐 **단언을
   완화해서 억지로 통과시키지 않는다.** 발견한 불일치를 그대로 사용자에게 보고하고, 테스트는
   실제로 기대되는 동작(스토리에 쓰인 대로)을 계속 단언한 채로 둔다. 버그를 감추는 테스트는
   테스트가 없는 것보다 나쁘다.
3. 실패가 간헐적이고(같은 테스트가 어떤 실행에서는 통과) 특히 "요소는 visible/enabled/stable로
   확인됐는데 클릭 자체가 타임아웃"되는 패턴이라면, 테스트 로직이 아니라 **화면이 테스트
   도중 알 수 없는 이유로 새로고침되며 React 상태(선택된 노트 등)가 날아갔을 가능성**을
   의심한다. 이 프로젝트에서 실제로 이 증상의 원인은 `db.json`이었다 — Vite 개발 서버가
   프로젝트 루트를 기본 감시하는데, `db.json`은 json-server가 노트를 생성/수정/삭제할 때마다
   다시 쓰는 런타임 파일이라 E2E 실행 중 잦은 쓰기가 Vite의 전체 새로고침(full reload)을
   유발했다(`vite.config.ts`의 `server.watch.ignored`에 이미 `db.json` 제외 처리를 해뒀다).
   같은 증상이 다시 보이면 먼저 이 설정이 유지되고 있는지 확인하고, 그래도 재현되면 프로젝트
   루트에 새로 생긴 다른 런타임/출력 파일(예: 로그 파일)이 같은 문제를 일으키는지 의심한다.
   워커 수를 줄이는 것은 증상을 가릴 뿐 원인을 고치지 못하므로 마지막 수단으로만 고려한다.

## 7단계 — 문서화 및 보고

`docs/features/{기능명}/prd.md` 하단에 "## E2E 커버리지" 섹션을 추가(이미 있으면 갱신)한다:

```markdown
## E2E 커버리지

- 스토리 1 (태그 자유 추가) → `e2e/tag.spec.ts`: `should show the new tag chip immediately
after pressing Enter`
- 스토리 3 (태그 목록 조회) → `e2e/tag.spec.ts`: `should display existing tags when opening
a note` (근거: 이슈 #7은 아직 열려 있으나 TAG-1 구현에 포함된 동기화 로직으로 실제로는
  이미 동작함 — 이슈 상태와 코드 불일치)
- 스토리 6 (생성 시 태그 동시 저장) → 제외: TAG-4(#8) 미구현, 생성 화면에 `TagInput`이
  아직 노출되지 않음
```

마지막으로 사용자에게 요약 보고한다: 몇 개 스토리 중 몇 개가 구현되어 있었는지, 그중 몇 개를
E2E로 옮겼는지, 실행 결과, 이슈 상태와 코드가 어긋난 부분이 있었는지, 제외한 스토리와 이유.

## 제약

- `src/`의 구현 코드를 수정하지 않는다.
- `*.test.ts` / `*.test.tsx`(Vitest)를 작성하거나 수정하지 않는다 — 그 계층은 이미 끝난
  단계다.
- 아직 구현되지 않은 스토리를 위한 테스트를 미리 써두지 않는다(실패가 예정된 E2E는 남기지
  않는다). 그런 스토리는 "제외" 목록에만 남긴다.
- `playwright.config.ts`의 전역 설정(브라우저 프로젝트, `webServer`, `baseURL`, `reporter`)을
  바꾸지 않는다. 이미 되어 있는 설정을 사용할 뿐이다.
- `e2e/support/fixtures.ts`가 이미 있다면 임의로 다시 만들지 않는다. 확장이 필요하면 무엇을
  왜 바꾸는지 사용자에게 먼저 알린다.
- 커밋, PR 생성을 하지 않는다.
