  후보를 찾아 개발자 승인을 받은 뒤, 한 번에 하나씩 고치고 즉시 `npm test`로 통과를
  재확인한다. 테스트가 깨지면 그 변경만 즉시 롤백하고 다른 접근을 시도하거나 건너뛴다. TDD
  Red-Green-Refactor 사이클의 마지막 단계를 시작할 때, 또는 "리팩토링하자", "코드 정리해줘",
  "구조 좀 개선하자", "TDD 리팩터 단계 시작" 같은 요청이 오면 명시적으로 스킬 이름을 부르지
  않아도 사용한다. 이미 통과하는 테스트를 깨지 않는 선에서 `src/`의 기존 코드 구조만
  바꾸며, 새 기능을 추가하거나 테스트 파일(`*.test.ts`/`*.test.tsx`)을 고치거나 이번 이슈의
  diff 범위 밖 파일을 건드리지 않는다. `npm test`가 아직 전부 통과하지 않는다면(Green 단계가
  안 끝났다면) 먼저 `/tdd-green`부터 실행하도록 안내한다.

# /tdd-refactor

Green 단계가 남긴 "통과하는 테스트 스위트"는 "동작이 이렇게 유지되어야 한다"는 계약이다. 이
스킬은 그 계약을 어기지 않는 범위 안에서만 코드 구조를 바꾼다 — 테스트가 계속 초록이라는
사실 자체가 "동작은 그대로다"의 유일한 증거이므로, 테스트를 건드려서 초록을 유지하는 건
반칙이고 새 동작을 추가해서 초록을 넓히는 것도 이 단계의 일이 아니다.

```
통과하는 테스트 스위트 (Green 완료) + CLAUDE.md (컨벤션) + git diff main...HEAD (이번 이슈 범위)
    ↓ 0단계 — 이슈가 속한 feature 찾기 (보고용)
    ↓ 1단계 — CLAUDE.md 읽기 → 프로젝트 컨벤션 파악
    ↓ 2단계 — npm test 실행 → 전체 통과부터 확인
    ↓ 3단계 — git diff 기반으로 리팩토링 대상 파일 식별 → 5개 기준으로 후보 도출
    ↓ 4단계 — 후보 목록 보고 → [GATE] 승인 대기
    ↓ 5단계 — 승인된 항목 하나씩: 변경 → npm test → 통과 확인 → 다음
    ↓ 6단계 — 테스트가 깨지면 그 항목만 즉시 롤백 → 재시도 또는 스킵
    ↓ 7단계 — 전후 변경 요약
동작 동일 + 구조 개선된 코드 (Refactor 완료, TDD 사이클 종료)
```

## 언제 쓰나

- `/tdd-green`으로 테스트가 전부 통과하는 상태에서, 커밋하기 전에 구조를 정리하고 싶을 때
- "리팩토링하자", "코드 정리해줘", "TDD 리팩터 단계 시작하자" 같은 요청이 올 때
- `/tdd-refactor {N}`으로 직접 호출되었을 때

이 스킬이 하지 않는 것: 새 기능 추가(그건 새 이슈로 `/test-scenarios`부터 다시 시작할 일),
테스트 파일 수정(테스트는 "동작이 안 바뀌었다"를 보증하는 심판이므로 리팩토링 주체가 심판을
같이 고치면 그 보증이 무효가 된다), 이번 이슈에서 손대지 않은 파일 수정.

## 입력

`$ARGUMENTS`: GitHub 이슈 번호 (예: `5`).

## 0단계 — 이슈가 속한 feature 찾기 (보고용)

`/tdd-red`/`/tdd-green`과 동일한 방법을 쓴다: `gh issue view {N}`으로 제목을 확인하고,
`docs/features/*/issues.md`에서 소속 feature를 찾는다. 이 값은 7단계 요약에서 "이슈 #{N}
({feature-name})"처럼 표기하는 용도일 뿐이다 — 리팩토링 대상 자체는 3단계의 `git diff`로
정해지므로, 시그니처·시나리오 문서를 다시 읽을 필요는 없다.

## 1단계 — 프로젝트 컨벤션 파악

리포지토리 루트의 `CLAUDE.md`(하위 디렉토리에 더 구체적인 `CLAUDE.md`가 있다면 그것도)를
읽는다. 이 스킬이 "정리"라고 부르는 것은 개인 취향이 아니라 **이 프로젝트가 이미 정해둔
패턴에 맞추는 것**이어야 한다 — 예를 들어 이 프로젝트라면 컴포넌트는 named export만
쓴다거나, 콜백 prop은 `onX`/구현부는 `handleX`로 짝을 맞춘다거나, 서버 상태는 Context에만
두고 UI 상태는 로컬 `useState`로 분리한다거나 하는 규칙들이다. 3단계에서 "컨벤션 불일치"를
판단할 기준이 바로 여기서 읽은 내용이므로, 이 단계를 건너뛰고 일반적인 클린 코드 감각만으로
판단하지 않는다.

## 2단계 — 전체 테스트 통과 확인

`npm test`(=`vitest run`, 전체 스위트)를 실행한다. 하나라도 실패하면 이 스킬을 시작할 조건이
안 된 것이다 — Green 단계가 아직 안 끝났거나 그사이 뭔가 회귀됐다는 뜻이므로, 리팩토링을
시작하지 말고 사용자에게 알린다. 이 스킬은 "이미 전부 초록"인 상태에서 시작한다는 전제 위에
서 있다.

## 3단계 — 리팩토링 대상 식별

```bash
git diff main...HEAD --name-only -- src/
```

로 이번 브랜치가 `main`에서 갈라진 뒤 `src/` 안에서 실제로 변경된 파일만 추린다 — 저장소
전체를 훑지 않는 이유는, 이번 이슈와 무관한 기존 코드까지 손대기 시작하면 리뷰 범위가
무한정 넓어지고 "이 변경이 왜 여기 있는지" 추적이 안 되기 때문이다. 결과에서
`*.test.ts`/`*.test.tsx`는 제외한다.

브랜치가 `main`에서 갈라지지 않았거나(예: 이미 `main` 위에서 작업 중) 결과가 비어 있으면,
추측해서 다른 범위를 잡지 말고 사용자에게 무엇을 리팩토링 대상으로 볼지 확인한다.

남은 파일 각각에 대해 다음 다섯 기준으로 후보를 찾는다:

- **중복 제거**: 같은 로직이 두 곳 이상에서 반복되는가.
- **네이밍 명확성**: 변수/함수/컴포넌트 이름이 의도를 드러내는가, 아니면 읽는 사람이 본문을
  봐야 뭘 하는지 알 수 있는가.
- **단일 책임**: 하나의 함수/컴포넌트가 서로 다른 이유로 바뀔 만한 여러 일을 한꺼번에 하고
  있는가.
- **불필요한 복잡도**: 매직 넘버, 과도한 중첩, 지금 필요하지 않은 추상화(아직 쓰이지 않는
  옵션/설정, 한 곳에서만 쓰이는 인터페이스 등).
- **CLAUDE.md 컨벤션 불일치**: 1단계에서 확인한 프로젝트 패턴과 어긋나는 코드.

각 후보는 "파일:대략적 위치 — 무엇이 문제고 어떻게 바꿀지 한 줄"로 정리한다. 이 시점에는
아직 코드를 고치지 않는다 — 목록만 만든다.

## 4단계 — 후보 보고 → [GATE] 승인

정리한 후보 목록을 사용자에게 보여주고 승인을 기다린다. 여기서 멈추는 이유는, 리팩토링은
"틀렸다/맞았다"가 아니라 "지금 이 정도로 정리하는 게 맞는가"라는 판단이 섞이는 영역이라서다
— 사용자가 일부 후보만 골라 승인하거나, 범위를 줄이거나, 아예 다른 방향을 제안할 수 있다.
승인되지 않은 항목은 5단계로 넘어가지 않는다.

## 5단계 — 하나씩 적용 → 즉시 검증

승인된 항목을 **하나씩** 처리한다. 여러 항목을 한 번에 묶어서 고치지 않는 이유는 단순하다 —
나중에 테스트가 깨졌을 때 방금 만든 다섯 개의 변경 중 어느 것이 원인인지 알 수 없게 되기
때문이다.

각 항목마다:

1. 코드를 변경한다. 이 단계에서 지켜야 할 것: 동작을 바꾸지 않는다(입출력, 렌더링 결과,
   호출되는 함수와 인자가 리팩토링 전후로 동일해야 한다), 새 분기나 옵션을 끼워 넣지 않는다.
2. `npm test`(전체 스위트)를 실행한다.
3. 전부 통과하면 다음 항목으로 이동한다.
4. 하나라도 실패하면 6단계로 간다.

## 6단계 — 실패 시 즉시 롤백

테스트가 깨지면 그 항목의 변경만 되돌린다. 이 시점에 대상 파일들은 직전 커밋(Green 완료
상태) 이후 아직 커밋되지 않은 상태이므로, 보통 `git checkout -- <파일>`로 그 파일만 원래
상태로 복원하면 된다.

- 되돌린 뒤, 같은 후보를 다른 방식으로 한 번 더 시도할 수 있다. 다만 같은 항목에 대해 **최대
  2회**까지만 재시도한다 — 그 이상 반복해도 안 된다면 리팩토링 자체가 이 시점에 적절하지
  않다는 신호이므로, 그 항목은 건너뛰고 사유를 남겨 7단계에서 보고한다.
- 절대로 테스트 코드를 수정해서 통과시키지 않는다. 테스트가 깨졌다는 건 방금 바꾼 코드가
  동작을 바꿨다는 뜻이고, 리팩토링의 정의(동작은 그대로, 구조만 개선)를 어긴 것이다.

## 7단계 — 전후 변경 요약

사용자에게 다음을 요약해서 보여준다:

- 승인된 후보 수, 실제로 적용된 수, 건너뛴 수(+ 각 사유)
- 파일별로 무엇을 바꿨는지 간단한 diff 요약
- 마지막 `npm test` 결과(전체 통과 확인)

## 제약

- **새 기능을 추가하지 않는다.** 리팩토링 중에 "이것도 있으면 좋겠다" 싶은 게 보여도 이
  스킬 밖의 일이다 — 새 이슈로 `/test-scenarios`부터 시작해야 한다.
- **테스트 파일(`*.test.ts` / `*.test.tsx`)을 수정하지 않는다.** 테스트가 "동작이 안 바뀌었다"
  를 보증하는 유일한 장치이므로, 리팩토링하는 쪽이 그 장치를 같이 손대면 검증이 무의미해진다.
- **`src/` 디렉토리 밖을 수정하지 않는다.**
- **3단계 `git diff` 결과에 없는 파일은 수정하지 않는다.** 지나가다 발견한 다른 파일의
  문제는 고치지 말고 사용자에게 보고만 한다 — 이번 이슈의 리팩토링 범위가 아니다.
- 후보를 찾다가 "이 컨벤션 자체가 이상한 것 같다"는 생각이 들어도 이 스킬 안에서 컨벤션을
  재정의하지 않는다. 발견한 내용은 보고만 한다.

## 참고

- 이 스킬은 `/tdd-green`(실패하는 테스트를 최소 구현으로 통과시키기) 바로 다음 단계이자, TDD
  Red-Green-Refactor 사이클의 마지막 단계다.
- `git diff` 기준을 `main`으로 잡는 이유: 이 프로젝트는 feature 브랜치에서 작업한 뒤 `main`으로
  PR을 올리는 흐름이라, `main` 대비 diff가 "이번 이슈에서 실제로 손댄 범위"를 가장 정확하게
  근사한다.
- 이 스킬이 끝나면 "동작은 동일하고 구조만 개선된 코드"가 남는다. 이후 커밋·PR 생성은 이
  스킬의 범위 밖이며, 별도 지시 없이 자동으로 진행하지 않는다.
