  끝나고 커밋하기 직전, 또는 "커밋 전에 점검하자", "타입 에러랑 취약점 확인해줘", "보안
  게이트 돌려줘", "커밋해도 되는지 확인해줘" 같은 요청이 오면 명시적으로 스킬 이름을 부르지

  않는다 — 이 스킬은 순수하게 점검·분류·(승인된 것만) 수정까지만 한다.

# /tdd-security-gate

`/tdd-refactor`까지 끝나면 코드는 "동작이 맞고 구조도 정리된" 상태지만, 그게 곧 "커밋해도
안전하다"는 뜻은 아니다. 타입 오류는 빌드를 깨뜨리고, 의존성 취약점과 노출된 비밀값은 코드
품질과 무관하게 실제 위험이다. 이 스킬은 그 마지막 확인을 기계적으로 수행하고, 무엇을 고칠지
판단이 필요한 부분은 사람에게 넘긴다 — 보안·빌드 관련 결정을 스킬이 혼자 내리고 조용히
고쳐버리면, 왜 그 코드가 바뀌었는지 아무도 모르는 채로 커밋에 섞여 들어간다.

```
Refactor 완료 코드 (커밋 전) + $ARGUMENTS(이슈 번호, 보고용)
    ↓ 0단계 — 이슈가 속한 feature 찾기 (보고용)
    ↓ 1단계 — npx tsc --noEmit → 타입 오류 수집
    ↓ 2단계 — npm audit → 의존성 취약점 수집
    ↓ 3단계 — .env 변수의 src/ 노출 여부 grep 점검
    ↓ 4단계 — 즉시 수정 필요 / 권장 수정 / 무시 가능 세 등급으로 분류해 보고
    [GATE] "즉시 수정 필요" 항목 승인
    ↓ 5단계 — 승인된 항목만 수정
    ↓ 6단계 — 재스캔 → 클린 상태 확인
커밋 가능한 코드 (보안 게이트 통과)
```

## 언제 쓰나

- `/tdd-refactor`가 끝나고 커밋하기 직전, 마지막으로 한 번 더 점검하고 싶을 때
- "커밋 전에 점검하자", "타입 에러랑 취약점 확인해줘", "보안 게이트 돌려줘" 같은 요청이 올 때
- `/tdd-security-gate {N}`으로 직접 호출되었을 때

이 스킬이 하지 않는 것: 코드 구조 개선(그건 `/tdd-refactor`의 일), 새 기능 추가나 시나리오
판단(AC 충족 여부는 `ac-verifier`의 일). 이 스킬은 오직 "빌드가 되는가, 알려진 취약점이
있는가, 비밀값이 새고 있는가"만 본다.

## 입력

`$ARGUMENTS`: GitHub 이슈 번호 (예: `5`).

## 0단계 — 이슈가 속한 feature 찾기 (보고용)

`/tdd-refactor`와 동일한 방법을 쓴다: `gh issue view {N}`으로 제목을 확인하고,
`docs/features/*/issues.md`에서 소속 feature를 찾는다. 이 값은 최종 보고에서 "이슈 #{N}
({feature-name}) 보안 게이트 결과"처럼 표기하는 용도일 뿐이고, 이후 점검 자체는 이슈 범위와
무관하게 프로젝트 전체(`tsc`, `npm audit`)와 `src/` 전체(`.env` 노출)를 대상으로 한다 — 타입
오류나 의존성 취약점은 "이번 이슈가 건드린 파일"로 국한되는 문제가 아니기 때문이다.

## 1단계 — 타입 오류 수집

```bash
npx tsc --noEmit
```

출력된 오류를 그대로 수집한다. 타입 오류는 성격상 판단의 여지가 거의 없다 — 컴파일이 안
되면 빌드가 실패하므로, 나온 오류는 원칙적으로 전부 "즉시 수정 필요"로 분류한다(4단계에서
예외가 있다면 왜 예외인지 반드시 근거를 남긴다).

## 2단계 — 의존성 취약점 수집

```bash
npm audit
```

출력에서 취약점 목록과 각각의 severity(critical/high/moderate/low), 영향받는 패키지가
`dependencies`인지 `devDependencies`인지, 수정 가능 여부(`npm audit fix`로 해결되는지, 아니면
상위 패키지 업데이트가 아직 없는지)를 정리한다. 이 정보가 4단계 분류의 근거가 된다.

## 3단계 — `.env` 변수의 `src/` 노출 점검

1. 프로젝트 루트에서 `.env`, `.env.local`, `.env.example` 등 존재하는 파일을 찾아 정의된
   변수 이름 목록을 확인한다. 파일이 하나도 없으면 이 프로젝트는 아직 환경 변수를 쓰지
   않는다는 뜻이므로, 이 단계는 "해당 없음"으로 기록하고 4단계로 넘어간다.
2. Vite 프로젝트는 `VITE_` 접두사가 붙은 변수만 클라이언트 번들에 노출되도록 설계되어 있다
   (`import.meta.env.VITE_X`). 따라서 진짜 위험은 **`VITE_`가 붙지 않은(서버 전용으로 의도된)
   변수가 `src/` 안에서 참조되거나, `.env`에 적힌 실제 값이 `src/` 코드에 문자열로 그대로
   박혀 있는 경우**다.
   - `grep -rn "import.meta.env" src/`로 어떤 변수가 클라이언트 코드에서 실제로 쓰이는지
     확인하고, 그중 `VITE_` 접두사가 없는 것이 있으면 즉시 수정 후보로 표시한다.
   - `.env`(로컬 실제 값이 든 파일, `.env.example`이 아닌 것)에 값이 채워진 변수가 있다면,
     그 값을 `grep -rn` 대상 문자열로 삼아 `src/`에 하드코딩되어 있는지 확인한다. 이때
     찾아낸 실제 값 자체를 보고서나 대화에 그대로 노출하지 않는다 — "어느 파일 몇 번째
     줄에 `{변수명}`의 값으로 보이는 문자열이 하드코딩되어 있다"처럼 위치와 사실만 보고하고
     값은 마스킹한다.
3. 이 grep은 오탐이 흔하다(예: 변수명이 흔한 단어와 겹치는 경우, 주석·문서 안의 언급). 4단계
   분류에서 실제 노출인지 오탐인지 구분해 보고한다.

## 4단계 — 세 등급으로 분류해 보고

1~3단계에서 모은 항목을 아래 기준으로 나눈다. 기준은 "지금 당장 사람이 봐야 하는가"를
축으로 한다 — 등급을 매기는 것 자체는 스킬이 판단하지만, 그 판단에 따라 실제로 무언가를
고치는 건 다음 게이트를 통과해야만 한다.

- **즉시 수정 필요**: 빌드를 깨뜨리는 타입 오류 전부, `dependencies`(런타임에 실제로 실행되는
  패키지)에 있는 critical/high 취약점 중 non-breaking 수정이 가능한 것, `.env` 노출 점검에서
  실제 노출로 확인된 항목.
- **권장 수정**: `devDependencies`에만 있는 취약점(빌드 시점에만 쓰이고 사용자에게 배포되지
  않음), moderate/low severity 취약점, 아직 upstream 수정이 없는 취약점(당장 손댈 방법이
  없으므로 "권장"이지 "즉시"는 아니다).
- **무시 가능**: 조사 결과 실제 위험이 없는 것으로 확인된 오탐(예: `.env` grep에서 우연히
  변수명과 겹친 무관한 문자열), 이 프로젝트의 사용 패턴상 해당 취약점 경로 자체를 타지
  않는다고 근거를 들어 설명 가능한 경우. "그냥 귀찮아서"는 무시 가능의 근거가 아니다 — 왜
  안전한지 한 줄이라도 설명을 남긴다.

세 등급을 표로 정리해서 개발자에게 보여주고, **"즉시 수정 필요" 항목에 대해서만** 진행
승인을 받는다. "권장 수정"/"무시 가능" 항목은 기록만 하고 이 스킬 안에서 손대지 않는다 —
그건 별도로 시간을 내서 판단할 일이지, 커밋 게이트가 알아서 정리할 일이 아니다.

## [GATE] 즉시 수정 필요 항목 승인

개발자가 "즉시 수정 필요" 목록을 확인하고 승인해야 5단계로 넘어간다. 목록 중 일부만
승인하거나 다르게 분류해달라고 할 수도 있다 — 그 판단을 그대로 반영한다.

## 5단계 — 승인된 항목만 수정

- **타입 오류**: 오류가 가리키는 실제 원인을 고친다. 오류를 없애려고 `as any`나 `@ts-ignore`
  로 덮어씌우지 않는다 — 그건 오류를 고친 게 아니라 숨긴 것이다.
- **의존성 취약점**: `npm audit fix`(플래그 없이)만 사용한다. **`npm audit fix --force`는
  어떤 경우에도 실행하지 않는다** — major 버전을 강제로 올려 예고 없이 호환성을 깨뜨릴 수
  있고, 그건 이 스킬의 승인 범위(취약점 수정)를 벗어나는 별개의 변경이다. `npm audit fix`로
  해결되지 않는 항목은 상위 패키지 업데이트가 필요하다는 뜻이므로, 스킬 안에서 억지로
  해결하려 하지 말고 개발자에게 별도 작업으로 안내한다.
- **`.env` 노출**: 하드코딩된 값을 `import.meta.env.VITE_X` 참조로 바꾸거나(클라이언트에 꼭
  필요한 값이라면), 애초에 클라이언트에 노출되면 안 되는 값이라면 `src/`에서 그 참조 자체를
  제거하고 서버 사이드로 옮겨야 한다는 사실을 개발자에게 보고한다 — 이런 구조 변경은 이
  스킬의 기계적 수정 범위를 넘어서므로, 직접 옮기지 말고 위치와 이유를 정확히 짚어 보고한다.
- **테스트 파일(`*.test.ts` / `*.test.tsx`)은 수정하지 않는다.**

## 6단계 — 재스캔

5단계에서 수정한 뒤 1~3단계를 다시 실행한다. "즉시 수정 필요"로 분류됐던 항목이 전부
사라졌는지 확인한다. 남아있다면(예: `npm audit fix`가 일부만 해결) 그 사실을 그대로 보고하고
— 억지로 더 손대지 않는다. "권장 수정"/"무시 가능" 항목은 그대로 남아있는 게 정상이다.

마지막으로 다음을 사용자에게 요약해서 보여준다:

- 1~3단계에서 발견된 항목 수 (등급별)
- 승인받아 실제로 수정한 항목과 그 내용
- 재스캔 후 남은 "즉시 수정 필요" 항목(있다면 이유 포함)
- "권장 수정"/"무시 가능"으로 분류돼 이번에 손대지 않은 항목 목록(다음에 참고할 수 있도록)

## 제약

- **판단이 필요한 항목은 반드시 개발자 승인 후에만 수정한다.** 등급을 매기는 것과 실제로
  코드를 고치는 것은 별개이며, 후자는 언제나 [GATE] 승인을 거친다.
- **테스트 파일을 수정하지 않는다.**
- **`npm audit fix --force`를 사용하지 않는다.**
- 이 스킬 안에서 새 기능을 추가하거나 리팩토링을 겸하지 않는다 — 발견한 오류를 고치는 데
  필요한 최소한의 변경만 한다.
- `.env` grep 과정에서 실제 비밀값을 확인하게 되더라도, 그 값 자체를 보고서·대화·커밋
  메시지 어디에도 그대로 남기지 않는다.

## 참고

- 이 스킬은 `/tdd-refactor`(구조 개선) 바로 다음, 커밋 전 마지막 단계다.
- 전역/플러그인으로 제공되는 `security-review`(브랜치 전체의 pending 변경사항에 대한 범용
  보안 리뷰)와는 목적이 다르다 — 이 스킬은 TDD 사이클의 특정 이슈를 커밋하기 직전에 돌리는
  기계적·좁은 범위의 점검(타입/의존성/`.env` 노출)이고, `security-review`는 더 넓은 범위의
  일반 보안 리뷰다. 더 폭넓은 보안 검토가 필요하면 `security-review`를 별도로 쓴다.
