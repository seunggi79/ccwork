# /tdd-green

`/tdd-red`가 남긴 "실패하는 테스트 스위트"를 하나씩 통과시켜, 승인된 시그니처·시나리오를
실제로 동작하는 코드로 채우는 단계다. 여기서도 새로 설계하지 않는다 — 시그니처는 이미
`docs/features/{name}/issue-{N}.md`에 합의되어 있고, "무엇이 통과해야 하는가"는 이미 테스트
코드로 고정되어 있다. 이 스킬의 역할은 그 테스트가 요구하는 것 **그 이상도 이하도 아닌** 코드를
채우는 것뿐이다.

```
실패하는 테스트 스위트 (Red 완료) + docs/features/{name}/issue-{N}.md (시그니처/시나리오)
    ↓ 0단계 — 이슈가 속한 feature 찾기
    ↓ 1단계 — npm test 실행 → 실패 테스트 목록 확인
    ↓ 2단계 — collect 실패 감지 → 필요하면 stub 파일 생성
    ↓ 3단계 — 디자인 컨텍스트 로드 (한 번, UI 구현이 있을 때만)
    ↓ 4단계 — 실패 테스트 하나 선택 → 최소 구현
    ↓ 5단계 — 재실행 → 통과 + 회귀 없음 확인 (실패 시 최대 5회 재시도)
    ↓ 6단계 — 시나리오 문서에 완료 표시
    ↓ 7단계 — 다음 실패 테스트로 이동 (4단계부터 반복)
    ↓ 8단계 — 전체 통과 후 커버리지 측정 (참고용, 테스트 추가 금지)
    ↓ 9단계 — 결과 요약
통과하는 테스트 스위트 + 구현 코드 (Green 완료, Refactor 단계로 인계)
```

## 언제 쓰나

- `/tdd-red`로 실패하는 테스트가 이미 만들어져 있는 이슈에 대해 구현을 시작할 때
- "이슈 N번 이제 구현하자", "Green 단계 시작", "테스트 통과시켜줘" 같은 요청이 올 때
- `/tdd-green {N}`으로 직접 호출되었을 때

이 스킬이 하지 않는 것: 테스트 파일을 새로 만들거나 수정하는 것(그건 `/tdd-red`의 일),
시그니처나 시나리오를 바꾸는 것(그건 `/test-scenarios`의 일). 테스트를 통과시키기 위해
테스트 코드 쪽을 손보고 싶은 유혹이 들어도 참는다 — 테스트가 잘못된 것 같으면 코드를 고치지
말고 사용자에게 보고한다.

## 입력

`$ARGUMENTS`: GitHub 이슈 번호 (예: `5`).

## 0단계 — 이슈가 속한 feature 찾기

`docs/features/{name}/issue-{N}.md`의 `{name}`을 확정한다. `/tdd-red`/`/test-scenarios`와 동일한
방법을 쓴다: `gh issue view {N}`으로 제목을 확인하고, `docs/features/*/issues.md`에서 해당 이슈
번호나 제목을 찾아 소속 feature를 특정한다. 찾지 못하면 추측하지 말고 사용자에게 묻는다.

이 문서에 "## 시그니처 (승인됨)"과 "## 테스트 시나리오" 섹션이 없다면 아직 `/test-scenarios`가
끝나지 않은 것이므로, 먼저 그 스킬부터 실행하도록 안내하고 멈춘다.

## 1단계 — 실패 테스트 목록 확인

`npm test`(=`vitest run`, 전체 스위트)를 실행해 현재 실패 상태를 파악한다. 이 시점에 실패하는
테스트가 하나도 없다면 이미 Green 단계가 끝났거나 `/tdd-red`가 아직 실행되지 않은 것이므로,
사용자에게 확인한다.

## 2단계 — collect 실패 감지

Vitest는 테스트 파일이 import하는 모듈이 아예 존재하지 않으면 그 파일의 테스트를 개별적으로
채점하지 못하고 파일 전체를 "collect 실패"로 묶어버린다. 이 상태로 4단계를 시작하면 "지금
어떤 시나리오가 통과했고 어떤 게 남았는지"를 테스트별로 추적할 수 없다.

**감지 방법**: `docs/features/{name}/issue-{N}.md`의 "## 테스트 시나리오" 섹션에서 시나리오
불릿 총 개수를 센다. 이 프로젝트의 시나리오 문서는 `- [정상] 함수명 — should ...` 형식을
쓰고 실제 GFM 체크박스(`- [ ]`)는 쓰지 않으므로(참고: `/tdd-red`, `/test-scenarios` 산출물),
`- [정상]`/`- [경계]`/`- [예외]`로 시작하는 줄을 "체크박스 항목"으로 취급해 개수를 센다. 이
개수와 `npm test` 출력의 `Tests` 줄 숫자를 비교한다.

- **일치하면**: 모든 시나리오가 개별 테스트로 인식되고 있다는 뜻이므로 stub 없이 3단계로
  진행한다.
- **`Tests` 수가 더 적으면(또는 파일이 "failed to collect"로 표시되면)**: import 대상 구현
  파일이 없어서 생긴 collect 실패다. 시나리오 문서의 "시그니처 (승인됨)" 섹션에서 "신규 파일"로
  표시된 대상(예: `src/utils/tags.ts`, `src/components/TagInput.tsx`)을 찾아, **승인된 시그니처
  그대로** stub 파일을 만든다. stub은 타입이 맞아 컴파일·import가 되는 최소 형태면 충분하고,
  실제 로직을 넣지 않는다 (예: 함수는 `throw new Error('not implemented')`, 컴포넌트는 최소
  JSX 하나만 반환). 목적은 "테스트가 개별적으로 실행되어 각자의 이유로 실패하게" 만드는
  것뿐이다.
- stub을 만든 뒤 `npm test`를 다시 실행해 `Tests` 수가 시나리오 개수와 일치하는지 재확인한다.

## 3단계 — 디자인 컨텍스트 로드 (UI 구현이 있을 때만, 한 번)

이번 이슈의 시나리오 중 컴포넌트(`.tsx`) 관련 항목이 있다면, 실제 코드를 쓰기 전에 시각적
스펙을 한 번 확인해둔다. 순수 함수/유틸만 구현하는 이슈라면 이 단계를 건너뛴다.

1. `docs/design-system/`이 있으면 `design-system` 스킬
   (`.claude/skills/design-system/SKILL.md`)의 내비게이션을 따라, 지금 구현할 컴포넌트에 필요한
   파일(`colors.md`/`spacing.md`/`components.md` 등)만 골라 읽는다. 이 프로젝트는 디자인
   시스템이 여러 파일로 나뉜 디렉토리이지 단일 문서가 아니므로, 전체를 다 읽지 말고 관심사에
   맞는 파일만 확인한다.
2. `docs/features/{name}/issue-{N}.md`에 "디자인 참고" 같은 섹션이 있으면 함께 확인한다.
3. `CLAUDE.md`의 "스타일링" 절(Tailwind v4, `@theme` 토큰, 시맨틱 클래스명 패턴)도 참조한다.
4. 위 문서들이 전혀 없으면 이 단계를 건너뛰고 `CLAUDE.md`의 기존 컨벤션과 이웃 컴포넌트의
   기존 클래스 패턴(`NoteItem`, `NoteEditor` 등)만 따른다.

여기서 확인한 스펙(색상 토큰, 간격, 레이아웃, hover/press 등 상태 표현)은 4단계 구현 내내
그대로 적용한다 — 시나리오마다 다시 찾아보지 않는다.

## 4단계 — 실패 테스트 하나 선택 → 최소 구현

시나리오 문서에 나온 순서(정상 → 경계 → 예외) 그대로, **하나씩** 처리한다. 여러 테스트를
한꺼번에 통과시키려고 코드를 몰아 쓰지 않는다 — 그러면 어떤 변경이 어떤 테스트를 통과시켰는지
추적할 수 없고, 테스트가 요구하지 않는 코드를 "김에" 추가하기 쉬워진다.

- **딱 그 테스트가 요구하는 만큼만** 구현한다. 테스트가 아직 검증하지 않는 분기·옵션·엣지
  케이스를 미리 만들어두지 않는다 — 그건 아직 시나리오로 합의되지 않은 동작을 추측해서 넣는
  것이다.
- 시그니처(파라미터 타입, 반환 타입, Props 타입)는 `docs/features/{name}/issue-{N}.md`에 이미
  확정되어 있으므로 그대로 따른다. 구현하다가 시그니처가 실제로는 안 맞는다고 느껴져도 이
  스킬 안에서 시그니처를 바꾸지 않는다 — 발견한 사실을 기록해뒀다가 9단계에서 보고한다.
- UI 컴포넌트라면 3단계에서 확인한 디자인 스펙(Tailwind 클래스, 레이아웃 구조, 상태별 표현)을
  함께 적용한다. 디자인 문서에 명시되지 않은 시각적 요소(그림자, 애니메이션, 색상 등)를
  임의로 추가하지 않는다 — 없는 걸 채워 넣기보다는 이웃 컴포넌트의 기존 패턴을 따른다.
- 불필요한 추상화를 만들지 않는다. 비슷한 코드가 두세 줄 반복되는 정도는 그대로 둔다 — 지금
  통과시켜야 할 테스트가 요구하지 않는 헬퍼/베이스 클래스/설정 옵션을 미리 만들지 않는다.

## 5단계 — 재실행 → 통과 + 회귀 확인 (피드백 루프)

1. 방금 겨냥한 테스트 파일만 먼저 실행한다: `npx vitest run <테스트 파일 경로>`.
2. **아직 실패한다면**: 에러 메시지를 읽고 원인을 분석해 코드를 수정한 뒤 1번부터 다시
   실행한다. 이 재시도는 **같은 테스트에 대해 최대 5회**까지 허용한다.
   - 5회를 넘겨도 실패하면 멈춘다. 지금까지 시도한 원인 분석과 에러 메시지를 사용자에게
     보고하고, 다음 테스트로 임의로 건너뛰지 않는다 — 시그니처나 시나리오 자체가 잘못됐을
     가능성을 포함해 사용자 판단을 기다린다.
3. **통과하면**: `npm test`(전체 스위트)를 실행해 이번 변경이 이미 통과하던 다른 테스트를
   깨뜨리지 않았는지 확인한다. 회귀가 생겼다면 그 회귀도 원인 분석 대상이다 — 무시하고 다음
   시나리오로 넘어가지 않는다.

## 6단계 — 시나리오 문서에 완료 표시

`docs/features/{name}/issue-{N}.md`에서 방금 통과시킨 시나리오 줄을 찾아 앞에 `[x]`를 붙인다.

```markdown
- [x] [정상] addTag — should append the trimmed input as a new tag when input is a new, non-duplicate value
```

(이 프로젝트의 시나리오 문서는 원래 GFM 체크박스를 쓰지 않으므로, `[x]`를 새로 붙이는 것
자체가 "이 스킬이 처리했다"는 표시가 된다. 2단계에서 셌던 "체크박스 총 건수" 대비 지금까지
`[x]`가 붙은 줄 수를 세면 진행률을 알 수 있다.)

## 7단계 — 다음 실패 테스트로 이동

남은 실패 테스트가 있으면 4단계로 돌아간다. 3단계(디자인 컨텍스트 로드)는 이미 끝났으므로
다시 하지 않는다.

## 8단계 — 전체 통과 후 커버리지 측정

모든 시나리오를 통과시켰으면 `npx vitest run --coverage`를 실행한다 (이 프로젝트는
`@vitest/coverage-v8`가 이미 설정되어 있다 — `npm run test:coverage`로도 동일하게 실행된다).

- 리포트에서 미커버 라인을 확인한다.
- 미커버 라인이 시나리오 문서에 없는 케이스(즉 `/test-scenarios` 단계에서 놓친 AC나 분기)로
  보이면, 어떤 라인이 왜 안 커버됐는지 사용자에게 보고한다.
- **커버리지 수치를 올리기 위해 테스트를 추가하지 않는다.** 커버리지는 참고 지표일 뿐이고,
  테스트 코드 작성 자체가 이 스킬의 범위 밖(`/tdd-red`의 일)이다. 빠진 케이스를 발견해도 이
  스킬 안에서 테스트를 만들지 말고 보고만 한다.

## 9단계 — 결과 요약

사용자에게 다음을 요약해서 보여준다:

- 몇 개 시나리오 중 몇 개를 통과시켰는지, stub으로 새로 만든 파일이 있었는지
- 실제로 구현/수정한 `src/` 파일 목록
- 5회 재시도로도 못 넘긴 테스트가 있었다면 그 목록과 원인
- 커버리지 요약과, 있다면 시나리오에서 빠진 것으로 보이는 미커버 케이스

## 제약

- **`src/`의 구현 코드(및 2단계의 최소 stub)만 작성·수정한다.** 테스트 파일(`*.test.ts` /
  `*.test.tsx`)은 어떤 이유로도 고치지 않는다 — 테스트가 잘못된 것 같으면 코드를 맞추지 말고
  사용자에게 보고한다.
- **테스트가 요구하지 않는 기능을 구현하지 않는다.** "이렇게 하면 더 좋을 것 같아서" 추가하는
  분기, 옵션, 방어 코드는 전부 금지 — 그건 아직 합의되지 않은 시나리오다.
- **불필요한 추상화를 만들지 않는다.** 지금 통과시켜야 할 테스트가 요구하지 않는
  헬퍼/베이스/설정을 미리 만들지 않는다.
- **디자인 스펙은 적용하되 창작하지 않는다.** `docs/design-system/`이나 이슈 문서에 명시된
  스타일만 그대로 쓴다. 명시되지 않은 시각적 요소(그림자, 애니메이션, 색상 등)를 임의로
  추가하지 않는다.
- 시그니처·시나리오 문서 자체에 문제가 보여도 이 스킬 안에서 임의로 고치지 않는다 — 발견한
  문제는 사용자에게 보고만 한다.

## 참고

- 이 스킬은 `/tdd-red`(시나리오 → 실패하는 테스트) 바로 다음 단계다. `/tdd-red`가 남긴
  실패하는 테스트 스위트와 `/test-scenarios`가 만든 `docs/features/{name}/issue-{N}.md`를
  입력으로 받는다.
- 이 스킬이 끝나면 "통과하는 테스트 스위트 + 구현 코드"가 남는다. 이후 중복 제거·구조 개선을
  하는 Refactor 단계는 이 스킬의 범위 밖이다.
